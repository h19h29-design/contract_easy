## 1. 결론 요약

- draft 3건은 모두 **사전체크리스트-용역** 페이지(MI…331)에서 생성됐다. 이 시스템의 핵심인 **공사** 기준은 별도 표(MI…332)에 있으며 값이 완전히 다르다.
- `band.10a8cb4bc567f`(입찰 1억 미만)는 같은 페이지의 **다른 표**(중소기업제품 우선구매)에서 인용돼 주 계약방법 표와 모순된다. 폐기 또는 재작성 대상.
- 나머지 2건은 용역 기준으로는 대체로 일치하나 경계 표기(이하/초과)와 엔진 경계 처리(하한 포함·상한 미포함)가 어긋난다.
- 공사 밴드를 만들려면 공사 유형(종합/전문/전기 등) 구분이 필요한데 현재 스코프·입력 모델에 해당 축이 없다(§4).

## 3. 초안별 대조

### construction.method.band.10a8cb4bc567f — 입찰 [0, 100,000,000)

- 인용: "입찰 / 1억 미만 입찰" — **우선구매 표**에서 온 문장. 주 계약방법 표(2-B)에서 입찰은 "1억원 초과"다.
- `bd1e7d8d8af6e`(입찰 1억 초과)와 정면 모순: 둘 다 승인하면 어떤 가격이든 "입찰"이 되어 수의계약 밴드와 충돌.
- 판정: **폐기 권고**(우선구매 기준이 필요하면 별도 규칙 유형으로 재작성).

### construction.method.band.ac9cf514f78c1 — 수의계약 [0, 100,000,000]

- 인용: "2인이상 견적제출 수의계약 / 1억원 이하" — 2-B와 일치(용역 기준).
- 문제 1: 원문 "이하"(≤1억) vs 엔진 between 상한 미포함(<1억) → 추정가격 정확히 1억이면 어느 밴드에도 안 걸리거나 입찰로 오매칭. 상한을 100,000,001로 보정하거나 lte 조건으로 바꾸는 결정 필요.
- 문제 2: 하한 없음 — 원문은 2천만원 이하에 "1인견적제출 수의계약 가능"을 별도 표기. [0,1억]은 그 구간을 2인수의로만 매핑. 1인수의 밴드 추가 및 구간 분리 결정 필요.
- 문제 3: 출력값 "수의계약" vs 원문 "2인이상 견적제출 수의계약" — 출력 세분화 여부.
- 문제 4: 출처가 용역 표인데 규칙 ID는 `construction.*` — 용역용으로 ID·스코프를 정정하거나 폐기 후 공사 밴드로 재작성.

### construction.method.band.bd1e7d8d8af6e — 입찰 [100,000,000, 0]

- 인용: "입찰 / 1억원 초과" — 2-B와 일치(용역 기준). `[100M, 0]`은 엔진에서 상한 없음으로 처리됨.
- 문제 1: 원문 "초과"(>1억) vs 엔진 하한 포함(≥1억) → 1억 정확히는 원문상 수의인데 입찰로 매칭. 하한을 100,000,001로 보정하는 결정 필요.
- 문제 2: 위와 동일 — 용역 출처인데 `construction.*` ID.

## 4. 스키마 검토 필요

- 공사 표는 **공사 유형**(종합/전문/전기 등 그 밖)에 따라 수의 상한이 다르다(4억/2억/1.6억).
- 현재 `WizardInput.contractCategory`는 `construction|electric|fire|ict|other` — 종합공사 vs 전문공사 구분이 없다. `electric|fire|ict`는 "전기 등 그 밖의 공사"(1.6억)에 대응 가능하나 `construction`은 종합/전문을 구분 못 함.
- 선택지: (a) 입력에 공사 유형 필드 추가(스키마 변경), (b) `construction`을 보수적으로 전문공사 2억으로 처리하고 종합은 문구로 안내, (c) 공사 밴드는 REVIEW_REQUIRED 유지하고 용역 밴드만 정정 승인.
- 어떤 선택이든 코드/스키마 변경이면 별도 작업 항목으로 분리해야 한다 (규칙 승인과 무관).

## 5. 참고 — 엔진 경계 처리

- `between [lo,hi]`: `p >= lo && (hi<=0 ? true : p < hi)` — 하한 포함, 상한 미포함, hi≤0이면 상한 없음.
- 원문 "이하"는 상한+1 보정 또는 `lte` 사용, 원문 "초과"는 하한+1 보정 또는 `gt` 사용이 정확하다.
- `isValidActivatablePriceCondition`은 `estimated_price` 조건만 허용 — 다른 필드 조건은 활성화 불가.

## 6. 승인 절차

1. `/admin/rules`에 로그인(REVIEWER 이상).
2. 각 draft의 원문 URL을 열어 값·경계·예외를 직접 대조.
3. 수정이 필요하면 새 draft revision 생성(메서드-밴드 입력만으로 생성 가능).
4. reviewed → active는 ADMIN 2인 승인.
